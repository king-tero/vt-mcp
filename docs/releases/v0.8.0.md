# vt-mcp 0.8.0 — autonomous submission and recovery

Version 0.8 extends the existing VirusTotal-through-VTAI workflow so an agent can
submit authorized bytes, recover the account's receipt and read the selected
analysis through MCP. It reuses the VTAI identity, rights, quotas and submission
records. No new service, database, OAuth flow or VirusTotal API key is required.

The compatible remote service and local stdio share seven tools: the four report
lookups, `get_analysis`, **`submit_file(sha256, content_base64)`** and
**`get_submission(sha256)`**. Inline submission accepts at most **24,000,000 decoded
bytes**, with a matching SHA-256. Local stdio additionally exposes
**`submit_local_file(path, expected_sha256=None)`**, which copies a local regular
file and accepts at most **32,000,000 bytes**. The optional expected digest must
match the copy; remote HTTP never receives a local-path tool.

Submission tools have no per-call confirmation or consent argument. The task and
specific host permissions establish authority for standard public sharing; they
do not bypass host controls or change VTAI rights. Standard submission is not
confidential. Inline content also appears in MCP arguments; local-file submission
keeps those bytes out of the arguments but still sends them to VTAI and VirusTotal.

The existing CLI retains its interactive confirmation and noninteractive
acceptance/digest flags. Report lookups and the optional execution guard retain
their existing behavior: they do not start scans or upload files.

`exists` is an existing report, `submitted` registers an analysis ID, and
`submission_unknown` can remain uncertain. Recover by hash with `get_submission`
instead of resending. Neither the client nor server automatically retries an
ambiguous POST. `get_analysis` reads the selected registered analysis once; use
later reads within a finite task budget, preserving pending states and actual
engine coverage. Completion and zero detections do not establish safety.

Start with [Agy, Claude Code or Codex](https://github.com/king-tero/vt-mcp/blob/main/docs/clients.md), in that order, and follow the
[submission and recovery guide](https://github.com/king-tero/vt-mcp/blob/main/docs/analysis.md). Agy 1.1.27 uses stdio because its
tested HTTP header variables were sent literally. Claude Code and Codex have
historical five-tool coverage over both transports with v0.7.0. That evidence does
not validate the new seven/eight-tool workflow. Consult the
[current validation matrix](https://github.com/king-tero/vt-mcp/blob/main/docs/clients.md#validation-levels)
for the observed client, transport and environment scope. Package publication does
not establish that a native workflow or production deployment has been validated.
Local stdio preserves the same durable state as the submission CLI;
changing hosts or recovering a receipt does not establish another upload.

Distribution uses the [GitHub release](https://github.com/king-tero/vt-mcp/releases/tag/v0.8.0),
not PyPI. The release process requires successful CI for the exact main commit,
independent artifact QA, both existing public-fixture gates and evidence retention;
it publishes the same wheel/sdist without rebuilding and verifies installation.
No product source, wheel, log or dependency is submitted by that fixture-only gate.
